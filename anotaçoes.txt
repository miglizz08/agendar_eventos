1. IDEIA DO PROJETO

Nome: Organiza Eventos.
Contexto: projeto acadêmico de Programação Front-End 01.
Objetivo: permitir que um organizador cadastre festas e eventos e, futuramente,
que as informações fiquem acessíveis ao público pela interface do site.
Usuário principal: organizador de eventos.

O registro de um evento tem estes campos:

  id         Número que identifica cada evento na API.
  titulo     Nome do evento.
  data       Data do evento. Os exemplos usam AAAA-MM-DD.
  horario    Horário do evento. Os exemplos usam HH:MM.
  local      Onde acontecerá o evento.
  descricao  Texto com mais informações sobre o evento.

Hoje a API exige titulo, data, horario e local para criar um registro. O campo
descricao é aceito, mas não é exigido nem validado. O id é criado pelo servidor;
quem faz o cadastro não precisa enviá-lo.

O escopo inicial é o cadastro de eventos. Inscrições, ingressos, pagamentos e
contas de usuário não fazem parte do que está implementado.


2. VISÃO GERAL: COMO AS PARTES SE RELACIONAM

O projeto tem dois programas separados:

  Navegador -> front-end Next.js (porta 3000)
  Cliente HTTP -> back-end Express (porta 3001) -> array de eventos na memória

O front-end é a parte visual com as páginas que a pessoa abre no navegador. O
back-end recebe requisições HTTP, trabalha com os dados e devolve JSON. JSON é
um formato de texto usado para transportar objetos e listas entre programas.

No futuro, a página de eventos deverá pedir os dados à API e renderizá-los.
Esse fluxo ainda não existe: visitar /eventos no site mostra somente uma
mensagem provisória. Hoje é possível consultar, cadastrar e editar eventos diretamente
na API com um cliente HTTP, como o PowerShell.

Os dois servidores usam portas diferentes. Portanto, as URLs
http://localhost:3000 e http://localhost:3001 têm origens diferentes. O pacote
cors está instalado no back-end, mas não foi ativado. Quando o front-end passar
a fazer requisições à API pelo navegador, será necessário configurar essa
permissão ou escolher outra forma adequada de integração.

4. BACK-END: DO ARQUIVO À RESPOSTA

Tecnologia: Node.js executa JavaScript fora do navegador; Express ajuda a criar
o servidor e as rotas HTTP. O package.json usa "type": "module", por isso o
código pode escrever import express from 'express'.

Ao iniciar backend/index.js, acontece esta sequência:

  1) O código importa Express.
  2) Cria o array eventos com dois exemplos: Halloween (id 1) e festa junina
     (id 2). Cada exemplo possui os seis campos descritos na seção 1.
  3) Cria a aplicação com express().
  4) Ativa express.json(), que interpreta corpos JSON enviados à API e coloca
     os dados em req.body.
  5) Define proximoId como 3 e registra POST /eventos, GET /eventos
     e PUT /eventos/:id.
  6) Inicia o servidor na porta fixa 3001 com app.listen(3001, ...).

"Array" é uma lista. Aqui, eventos é a lista de registros existentes. Ela fica
na memória do processo do Node.js. Se o servidor for reiniciado, os cadastros
feitos durante a execução desaparecem e a lista volta aos dois exemplos.
Não há banco de dados ou arquivo usado para salvar novos eventos.

ROTA GET /eventos

GET significa pedir dados. Essa rota executa res.json(eventos) e responde com a
lista inteira em JSON, na ordem em que os itens estão no array. Não recebe id,
filtros ou parâmetros. A resposta normal tem status HTTP 200. Se nenhum POST
foi feito desde a inicialização, a lista contém só os dois exemplos.

ROTA POST /eventos

POST significa enviar dados para criar um recurso. O corpo esperado é JSON. A
rota lê titulo, data, horario e local de req.body usando ?. para evitar falha
ao tentar acessar uma propriedade de um corpo ausente. Depois verifica cada
campo nesta ordem: titulo, data, horario, local.

Para cada um dos quatro campos obrigatórios, a condição é: o valor precisa ser
uma string e não pode ficar vazia depois de trim(). trim() remove espaços nas
pontas para essa verificação. Se a condição falhar, a rota encerra com status
400 e um JSON como {"mensagem":"Título é obrigatório."}. O status 400 indica
que a requisição enviada não atende às regras da API.

Se os quatro campos passarem, a rota monta novoEvento com o id atual de
proximoId, copia os dados enviados, aumenta proximoId em 1, inclui o objeto no
array com push() e responde com status 201 e o novo evento em JSON. O status
201 significa que o recurso foi criado. Por exemplo, o primeiro cadastro
válido após iniciar o servidor recebe id 3; o seguinte recebe id 4.

Limites exatos da validação atual:

  - A verificação garante apenas tipo string e conteúdo não vazio após trim().
  - O valor original é salvo; o código não remove os espaços ao armazená-lo.
  - Não há checagem de formato ou existência real de data e horário.
  - descricao não tem validação. Se for omitida, o objeto terá valor undefined
    nessa propriedade; ao virar JSON na resposta, a propriedade é omitida.
  - Não há limite de tamanho, verificação de duplicatas ou persistência.

O exemplo de POST nas notas do início deste arquivo envia somente titulo.
Com o código atual, ele recebe erro 400 para data obrigatória. Isso mostra a
diferença entre uma requisição de teste incompleta e um cadastro válido.

6. CONTRATO ATUAL DA API: EXEMPLOS PARA MEMORIZAR

Endereço-base: http://localhost:3001

GET http://localhost:3001/eventos
Resposta: status 200 e uma lista JSON. Forma simplificada:

  [
    {"id":1,"titulo":"halloween","data":"2026-10-31",...},
    {"id":2,"titulo":"festa junina","data":"2026-06-12",...}
  ]

Os três pontos acima abreviam os demais campos apenas neste guia; a resposta
real contém os campos de cada evento.

POST http://localhost:3001/eventos
Cabeçalho: Content-Type: application/json
Corpo válido de exemplo:

  {
    "titulo": "Encontro de música",
    "data": "2026-11-15",
    "horario": "19:00",
    "local": "Centro cultural",
    "descricao": "Apresentações musicais abertas ao público."
  }

Se for o primeiro cadastro desde que o servidor iniciou, a resposta tem
status 201 e os mesmos dados acrescidos de "id": 3. Um corpo como
{"titulo":"Teste"} falha com status 400 e mensagem "Data é obrigatória."
porque a primeira validação, titulo, passa e a segunda, data, falha.

A edição já está disponível em PUT /eventos/:id (veja a seção 11). Ainda não
existem rotas para buscar um único evento pelo id ou excluí-lo. Também não há
autenticação.


7. COMO EXECUTAR E EXPERIMENTAR NO COMPUTADOR

Pré-requisito: Node.js e npm instalados. Abra dois terminais na pasta raiz do
projeto. npm ci instala as dependências registradas em cada package-lock.json.

Terminal 1, API:

  cd backend

Deve aparecer "API na porta 3001". Deixe esse terminal aberto.

Terminal 2, site (a partir da raiz do projeto):

  cd frontend
  npm ci
  npm run dev

Abra http://localhost:3000/eventos para ver a página provisória. Abra
http://localhost:3001/eventos para ver o JSON retornado pela API. O endereço
localhost aponta para o próprio computador onde os programas estão rodando.
Em outro dispositivo, como um celular, localhost aponta para aquele outro
dispositivo e não para o computador do projeto.

Exemplo de cadastro no PowerShell (com a API ligada):

  $evento = @{
    titulo = 'Encontro de música'
    data = '2026-11-15'
    horario = '19:00'
    local = 'Centro cultural'
    descricao = 'Apresentações musicais abertas ao público.'
  } | ConvertTo-Json
  Invoke-RestMethod -Uri 'http://localhost:3001/eventos' -Method Post -ContentType 'application/json' -Body $evento
  Invoke-RestMethod -Uri 'http://localhost:3001/eventos' -Method Get

O primeiro comando monta o corpo JSON; o POST cria o evento; o GET permite
conferir que ele entrou na lista. Reinicie a API e faça o GET novamente para

quatro campos obrigatórios são strings preenchidas.

O front-end oferece os comandos npm run build (gerar a versão de produção) e
npm run start (iniciar a versão gerada). O back-end não tem script start no
package.json: por enquanto ele é iniciado com node index.js. O script test do
back-end é apenas a mensagem padrão "no test specified"; não há testes
automatizados implementados.


8. CONCEITOS QUE VALE ENTENDER

API: interface pela qual um programa oferece operações a outro. Neste projeto,
a API oferece listagem e cadastro em /eventos, além de edição em
/eventos/:id.

Rota: combinação de método HTTP e caminho. GET /eventos e POST /eventos são
rotas diferentes mesmo compartilhando o caminho. PUT /eventos/:id usa o id
na URL para atualizar um evento específico.

Requisição e resposta: o cliente envia método, endereço e, no POST ou PUT, um corpo;
o servidor processa e devolve status e dados.

req e res: no Express, req representa a requisição recebida; res permite montar
a resposta. req.body contém os dados JSON interpretados por express.json().

Status HTTP: número que informa o resultado. Aqui, 200 é consulta ou edição
bem-sucedida, 201 é criação, 400 indica dados rejeitados e 404 indica que o
evento solicitado para edição não foi encontrado.

Estado em memória: dados guardados em uma variável durante a execução. É
simples para aprender, mas não sobrevive ao reinício do processo.

Front-end e back-end: o primeiro desenha e recebe interações na interface; o
segundo aplica as regras e mantém os dados do servidor.

CORS: mecanismo do navegador que controla certas requisições entre origens
distintas. Ele será relevante na integração da página com a API, pois as
portas 3000 e 3001 formam origens diferentes. Comandos PowerShell não dependem
da política de CORS do navegador.

11. ATUALIZAÇÃO DE 07/10/2026: EDIÇÃO DE EVENTOS

O que entrou: a rota PUT /eventos/:id em backend/index.js. PUT é o método HTTP
usado aqui para atualizar um evento já cadastrado. O trecho :id é o parâmetro
da URL: PUT /eventos/1 tenta editar o registro cujo id é 1. O servidor lê
req.params.id e o converte para número com Number().

Corpo esperado: envie titulo, data, horario e local como strings preenchidas.
Mesmo que você queira mudar somente o local, precisa reenviar os quatro
campos. A descricao é opcional; se for enviada, deve ser string. Uma string
vazia é aceita. O id fica na URL, não no corpo.

Ordem do código:

  1) Lê o id da URL e os campos do corpo JSON.
  2) Valida titulo, data, horario e local nessa ordem. Cada valor precisa ser
     string e não pode ficar vazio após trim(). Um erro devolve status 400.
  3) Se descricao foi enviada com tipo diferente de string, devolve 400.
     Isso inclui o valor null.
  4) Procura o objeto no array com eventos.find(e => e.id === id).
     Se não encontrar, devolve 404 e {"mensagem":"Evento não encontrado."}.
  5) Se encontrar, altera as propriedades do próprio objeto, preserva o id e
     devolve o evento atualizado com status 200.

Como as validações ocorrem antes de eventos.find(), um corpo inválido enviado
para um id inexistente recebe 400 antes de receber 404. O texto exato de
algumas mensagens de erro do PUT contém erros de acentuação e digitação no
código atual; consulte backend/index.js se precisar reproduzi-las.

A expressão descricao ?? '' grava uma string vazia quando descricao é omitida.
O id não muda, proximoId não aumenta e nenhum novo item entra no array. Como
o array fica só na memória, as edições desaparecem quando a API reinicia.

Exemplo de teste no PowerShell, com a API ligada:

  $edicao = @{
    titulo = 'Halloween atualizado'
    data = '2026-10-31'
    horario = '20:00'
    local = 'Salão principal'
    descricao = 'Festa com fantasia e música.'
  } | ConvertTo-Json
  Invoke-RestMethod -Uri 'http://localhost:3001/eventos/1' -Method Put -ContentType 'application/json' -Body $edicao
  Invoke-RestMethod -Uri 'http://localhost:3001/eventos' -Method Get

O GET final permite ver a alteração. Para testar o caso de não encontrado,
troque /1 por /999 e envie o mesmo corpo válido: a resposta será 404.

Limites atuais: não há verificação de formato real de data, horário ou id.
Um id não numérico é convertido para NaN e não encontra evento. Um corpo
totalmente ausente pode causar erro do servidor ao desestruturar req.body, em
vez de uma resposta 400. Ainda não há botão ou formulário de edição no
front-end; a rota é usada diretamente por um cliente HTTP.
